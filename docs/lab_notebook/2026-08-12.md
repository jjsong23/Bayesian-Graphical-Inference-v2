## 1. Posterior-probability distribution plots

### Rationale

The GUI previously reported selected-node counts, supported-edge counts, and
ranked paths, but it did not expose the shapes of the posterior distributions.
This made it difficult to distinguish a run in which most hypotheses remained
at the neutral 0.5 prior from a run with broad but modest probability changes.

### Implementation

A reusable server-side probability summary was added for both node and edge
hypotheses. Each summary contains:

- the number of hypotheses;
- minimum, mean, and maximum posterior probabilities;
- the configured prior and output cutoff;
- the number exactly equal to the prior;
- the number strictly above the output cutoff; and
- counts in 50 fixed, equal-width bins spanning 0 to 1.

The node distribution includes all candidate protein hypotheses, not only
selected nodes. The edge distribution includes every unique unordered pair in
the final graph and excludes the diagonal. Consequently, an undirected pair is
counted once in the distribution even though its probability appears twice in
the symmetric adjacency matrix.

The browser now renders separate SVG histograms for node and edge posterior
probabilities. Bar heights use `log10(count + 1)` so that the large neutral bin
does not visually obscure smaller supported bins. Hover text gives the actual
bin interval and untransformed count. A dashed orange line marks the configured
output cutoff, and the cards display the exact-prior count, above-cutoff count,
mean, and range. The underlying Bayesian values are not log transformed; the
logarithm is only a display transformation for histogram height.

The summaries are included in both the live GUI preview and each run's
`analysis_summary.json`, so the visualizations can be reconstructed without
rerunning the analysis.

## 2. Separating edge existence from propagation direction

### Modeling decision

The existing Bayesian edge analysis answers an undirected binary question:
does an association between nodes A and B exist? That model and its symmetric
adjacency matrix were preserved.

Directionality was added as a separate path-search layer. For an undirected
edge with posterior probability `p`:

- if the ontology catalog uniquely supports A → B, the propagation matrix
  stores A → B as `p` and B → A as 0;
- if it uniquely supports B → A, the reverse assignment is made;
- if no rule applies, both traversals retain `p`; and
- if multi-role annotations produce rules in both directions, both traversals
  retain `p` and the pair is marked as conflicting.

Thus, the direction layer removes unsupported traversals but never raises,
lowers, or recomputes the Bayesian probability of the underlying association.
Activation and inhibition are also kept separate from direction. For example,
a phosphodiesterase-to-second-messenger relation has a negative biochemical
effect, but the current path score still uses only the retained edge
probability.

This partial orientation prevents a path search from traversing the forbidden
arm of a resolved collider or fork. It cannot eliminate collider/fork motifs
whose edges remain unresolved, so it should not be described as complete causal
orientation.

## 3. Ontology direction-rule catalog

### Role classes considered

The versioned catalog enumerates 17 ontology-derived classes:
`receptor`, `receptor_regulator`, `ligand`, `kinase`, `phosphatase`, `cyclase`,
`phosphodiesterase`, `phospholipase`, `nos`, `gtpase`, `gtpase_regulator`,
`kinase_phosphatase_binding`, `second_messenger_binding`, `signaling_process`,
`signaling_regulation`, `second_messenger`, and `adaptor_scaffold`.

The complete class-pair report contains all 153 unordered combinations with
replacement: `17 × 18 / 2 = 153`. This report shows both the combinations that
have active rules and those deliberately left unresolved.

### Active first-pass rules

| Source role | Target role | Interpretation |
|---|---|---|
| ligand | receptor | A ligand acts on its receptor. |
| receptor_regulator | receptor | A receptor regulator acts on its receptor. |
| kinase | kinase_phosphatase_binding | Project policy requested today: a kinase-binding node does not propagate toward the kinase. |
| phosphatase | kinase_phosphatase_binding | Analogous project policy for phosphatase-binding nodes. |
| gtpase_regulator | gtpase | A GEF, GAP, or other GTPase regulator acts on the GTPase. |
| cyclase | second_messenger | A cyclase produces a cyclic-nucleotide second messenger. |
| phospholipase | second_messenger | A phospholipase produces a lipid-derived second-messenger signal. |
| nos | second_messenger | Nitric-oxide synthase produces nitric oxide. |
| phosphodiesterase | second_messenger | A phosphodiesterase acts on and decreases a cyclic nucleotide; the negative sign is recorded but not yet scored. |
| second_messenger | second_messenger_binding | A second messenger acts on a connected binding protein. |

No standalone direction was assigned from `signaling_process`,
`signaling_regulation`, or `adaptor_scaffold`, because those broad labels alone
do not identify causal order. All other unmatched class combinations were also
left bidirectional.

These rules are transparent role heuristics, not causal statements formally
entailed by Gene Ontology. In particular, the kinase/phosphatase-binding rules
are explicit project modeling policies and should be re-evaluated when
curated directed interactions and substrate-specific evidence are integrated.

### Multi-role proteins

Every role label on each endpoint is evaluated. A pair is oriented only when
all matching evidence points one way. If one role combination supports A → B
and another supports B → A, the pair receives the status
`unresolved_conflicting_rules` and remains traversable in both directions.
This fail-open behavior prevents a multifunctional protein from being assigned
an arbitrary direction.

## 4. Software and output changes

The direction engine was implemented in
`code/path_finding/ontology_directionality.py`, with its versioned policy in
`code/path_finding/ontology_direction_rules.json`. It validates the catalog,
builds the 153-row class-pair report, applies the rules to supported edges, and
checks that no retained traversal differs from its original undirected
probability.

The standalone and GUI path-finding workflows now accept a partially directed
propagation matrix. The GUI includes an **Apply conservative ontology
directionality** switch, enabled by default. Turning it off restores the
previous fully bidirectional path search.

Each directional run writes four additional artifacts:

- `propagation_adjacency_matrix.tsv`: the partially directed matrix used by the
  path search;
- `ontology_directionality_audit.tsv.gz`: edge-level classes, matched rules,
  status, and allowed traversals;
- `ontology_class_pair_catalog.tsv`: all 153 class-pair decisions; and
- `ontology_direction_rules.json`: the exact policy used by that run.

The original symmetric edge-probability matrix and undirected supported-edge
table remain unchanged and are still written separately.

## 8. Interpretation and remaining limitations

The ontology-only layer established a unique direction for approximately 14.5%
of currently supported edges. This is useful but deliberately conservative:
most edges remain bidirectional because their ontology roles do not determine
causal order.

Important next evidence streams for directionality include curated OmniPath
source-target records, kinase-to-substrate phosphosite evidence, receptor-ligand
annotations with molecule-specific support, and explicit activation/inhibition
signs. Those streams should be integrated as auditable direction evidence and
should retain conflict information rather than silently overriding one another.

Finally, a high-probability directed path remains a model-ranked propagation
hypothesis, not proof that the signal travels along that route in collecting
duct cells. Experimental context, compartment accessibility, temporal order,
and biochemical sign still require independent validation.
